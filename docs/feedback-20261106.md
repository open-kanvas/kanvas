# November 6 feedback: 0.36.0

## Display/API contracts

- Toast remains an overlay, never a publication: optional `title` (160), `description` (1000), safe image URL/upload reference `icon`, ISO offset-aware `time` (viewer-local HH:mm). Legacy `text` (1000) works; description wins if both supplied. At least title/text/description required. Severity, dismissal, duration, 24-hour sticky expiry unchanged. Failed images hide independently. No service types or action links.
- QR portrait uses an actual parent size container; short title/text fits alongside a prominent code with the unchanged four-module quiet zone. Long prose can scroll rather than shrink modules indefinitely.
- Device privacy says “Kanvas is locked on this device. Ask your agent to unlock.” No account or private details shown.
- Connect Four empty wells are mid-gray, distinct from both neutral disc colors. Card fronts have corner rank/suit; unknown backs still contain no identity. Very deep solitaire stacks scroll rather than making indices illegible.
- Fretted boards with up to six displayed frets fit their width. Longer boards retain a readable scrollable subset. Subtle physical 3/5/7/9 markers repeat each octave; multiples of 12 use two dots, independent of capo and mirrored with handedness.
- Grid game `orientation: default|flipped` changes geometry only. Internal rROWcCOLUMN remains canonical. Friendly A1 aliases work on submit/patch; pieces expose derived `coordinate` alongside internal `cell` on readback. Chess/checkers/Go/reversi ranks remain bottom-up; others retain documented top-down coordinates. Card tables are unaffected. Orientation is view-wide, not a per-viewer preference.
- Public navigation read/control use one-based `state.page`, with explicit zero-based `pageIndex`. Browser internal protocol remains zero-based. No history change.
- New sessions store server-authoritative `serverVersion`; every new raw event has authoritative `properties.serverVersion`. No historical version backfill. Built browser exposes `meta[name=kanvas-version]`; registered windows report self-observed `clientVersion`, separate from window revision and server version.
- New feedback no longer has a category input; historical report categories/text remain retained. No classification or triage replacement.
- Only the root overview's “Account & console” link is removed. `/console?account=sessions` still reaches Signed-in browsers/device unlock; `/console` and its authorization are unchanged. Other existing links remain in consent, invitations, Start, help and console menus.
- Weather `display` accepts optional booleans `place`, `time`, `temperature`, `description`, `details`, `timeline`, plus `visualOnly`. Default shows submitted fields; temperature and place are optional. Description controls the condition heading too. Hidden timeline does not stop supplied forecast animation. Data is never removed by hiding it. Main reading is positioned above the horizon; eight details use a compact two-column layout.
- Checklist update remains save, show remains explicit. Only currently matching top-level checklist displays refresh, serialized with publication writes; other content wins, multiple displays/windows refresh, and no history row is added. Existing navigation roots/scroll/autofollow are preserved. Checklist snapshots inside presentations/split panes are not live document bindings in this first split release.

## Split screen

`split-screen` is a separate view with `data.direction: vertical|horizontal` (vertical means side-by-side) and 2/4/6 `panes: [{id,view}]`. Stable pane IDs preserve mounted sibling state. Four is 2×2; six is 3×2. Each pane renders the ordinary template in an empty same-origin iframe document with the application's styles: CSS viewport units/media queries are genuinely pane-local, not based on the outer window. No supplied scripts or arbitrary HTML enter that document.

Publish counts as one retained screen publication, never six. Existing aggregate JSON byte/node budgets still apply to the whole screen. No nested splits; presentations may contain ordinary leaves, never splits. Patch `/data/panes/0/view` for one pane or `/data/panes/0/view/data/...` for specific data, with normal expectedRevision/requestId guards. One patch counts as one screen mutation; unchanged sibling panes do not reset. Pane IDs/count change through a new submission.

Below 600 CSS px the screen uses labelled pane-selector buttons and keeps one readable pane visible; hidden panes remain mounted. Pane intrinsic/local scrolling and media controls work, but server-bound form/poll/QA responses and editing are disabled in panes. Global pointing/page/scroll tools do not address inner iframe contents; zoom scales the complete display. Device privacy and display lockdown apply to the whole screen. No separate pane history or per-pane control tools are introduced.

## Database schema

New `database-schema` is independent of architecture and takes a plain `columns` list: optional schema, table, column, type, nullable, optional primaryKey/foreignKey/default. Optional relationships have explicit `{from,to,kind:'declared'|'inferred',label?}` column endpoints. No relationships are inferred by Kanvas. Solid/dashed lines distinguish declared/inferred, and an accessible linked relationship list names exact endpoints. Related/grid layout, up to 40 tables/500 columns/100 relationships; no silent truncation. Phone layout stacks readable table boxes and scrolls. Display only: no credentials, connector or SQL execution.

## Artwork retirement

The exact previously reviewed Apache-2.0 mapping has **88** sign types backed by **55** pinned Google Material Symbols SVGs. All 49 original glyph types are removed from catalog/schema and renderer source, with no option or fallback. This includes exit and first-aid/no-smoking: reporter guesses about which signs were replaced were not manifest verification. No uncertain ISO assets added. Historical saved views remain untouched and show a truthful unavailable state if they use a retired type. Manifest coverage marks them retired; credits show only offered artwork. Software rollback does not need data restoration but will restore the older renderer's capabilities; avoid rewriting historical sources.

## Standard OAuth investigation

The email-link tab and original connector tab are different roles. Standard email confirmation authorizes the originating browser, deliberately does not sign in the email-opening browser, and leaves that email tab in place. The original tab polls `/api/auth/email/status`, completes sign-in, approves the pending connection, then navigates to the callback returned by the server. Final signed-in consent likewise uses that exact returned redirect. Server validation of redirect/state/PKCE remains unchanged. Email-confirmation wording distinguishes approval from completion; originating/final-consent screens show a concise connected/next-step/close-window fallback before navigation. The email tab truthfully says to return to the original tab, rather than claiming an OAuth grant before it exists. Device-code flow is unchanged. Real Claude/ChatGPT focus/callback behavior needs owner interaction; isolated tests cannot establish provider acceptance.
